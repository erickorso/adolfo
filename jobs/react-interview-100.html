1. React — Fundamentos (1–15)

1. ¿Qué es React y por qué usarlo?

Librería UI basada en componentes declarativos. Virtual DOM + reconciliación minimizan manipulación directa del DOM. Ecosistema maduro, composición, SSR con Next.

2. ¿Virtual DOM vs DOM real?

React mantiene árbol JS en memoria. Tras un update compara (diff) y aplica solo cambios mínimos al DOM real (commit). No es más rápido siempre, pero simplifica UI compleja.

3. ¿Qué es JSX?

Sintaxis que parece HTML en JS. Se transpila a React.createElement. Una expresión por nodo; className en vez de class.

4. ¿Element vs Component?

Elemento: objeto ligero que describe qué renderizar. Componente: función/clase que devuelve elementos. <Button /> invoca la función del componente.

5. ¿Props vs State?

Props: entrada inmutable del padre. State: datos internos mutables vía setState/useState. Cambios en ambos disparan re-render.

6. ¿Unidireccionalidad de datos?

Datos bajan por props; eventos suben por callbacks. Facilita depuración y flujo predecible vs two-way binding clásico.

7. ¿Qué es reconciliación?

Algoritmo que compara árbol anterior y nuevo. Misma key + mismo tipo → actualiza props. Tipo distinto → desmonta y monta. Keys estables en listas evitan bugs.

8. ¿Por qué no usar index como key?

Reordenar/insertar/borrar reutiliza nodos incorrectos → estado mezclado, inputs corruptos, animaciones rotas. Usa ID estable del dato.

9. ¿Controlled vs Uncontrolled?

Controlled: React controla value + onChange. Uncontrolled: DOM guarda valor vía ref. RHF mezcla ambos para performance en forms grandes.

10. ¿Lifting state up?

Subir estado al ancestro común cuando dos hermanos deben compartirlo. Evita duplicar fuente de verdad.

11. ¿Composition vs Inheritance?

React favorece composición (children, render props, slots). No herencia de clases para extender UI.

12. ¿Strict Mode en dev?

Monta/desmonta y re-ejecuta efectos dos veces en dev para detectar side effects no idempotentes. No afecta producción.

13. ¿Error Boundaries?

Solo class components con getDerivedStateFromError/componentDidCatch capturan errores de render/hijos. No atrapan event handlers ni async. En App Router: error.tsx.

14. ¿Portals?

createPortal renderiza hijos fuera del DOM padre (modales, tooltips) manteniendo contexto React y event bubbling.

15. ¿React 19 novedades clave?

Actions, useActionState, useOptimistic, ref como prop, mejor hidratación, use para promises/context, document metadata en componentes.

2. Hooks (16–30)

16. Reglas de los Hooks

Solo en top-level (no en if/loops). Solo en componentes funcionales o custom hooks. Garantizan orden estable entre renders.

17. ¿useState batching?

Múltiples setState en un evento se agrupan en un solo re-render. React 18+: batching también en promises/timeouts.

18. ¿useEffect vs useLayoutEffect?

useEffect: tras paint (no bloquea). useLayoutEffect: tras DOM update, antes de paint — mediciones DOM, evitar flicker. En SSR ambos no corren en servidor.

19. Dependencias de useEffect

Array con todo valor externo usado. Omitir = cada render. [] = solo mount. ESLint exhaustive-deps ayuda; no silenciar sin razón.

20. Cleanup en useEffect

Return function para abortar fetch, quitar listeners, clearInterval. Evita memory leaks y race conditions.

21. ¿useRef vs useState?

useRef: mutable sin re-render (DOM refs, timers, flags). useState: cambio visible en UI. No leer/escribir ref.current durante render si afecta output.

22. ¿useMemo cuándo?

Cálculo caro o referencia estable para memo/deps. No por defecto en todo — coste de comparación. Perfil primero.

23. ¿useCallback cuándo?

Estabiliza función pasada a hijo memo o en deps de effect. Innecesario si el hijo no está memoizado.

24. ¿useReducer vs useState?

Reducer para estado complejo, transiciones explícitas, testing del reducer puro. Misma API de dispatch que Redux.

25. ¿Custom hooks?

Funciones use* que encapsulan lógica con hooks. Comparten comportamiento sin HOC/render props. Ej: useDebounce, useMediaQuery.

26. ¿useContext gotchas?

Cualquier cambio de valor re-renderiza todos los consumidores. Split contexts (theme vs user). No para datos de alta frecuencia.

27. ¿useId?

IDs únicos estables SSR/cliente para htmlFor/aria-*. Evita colisiones en hidratación.

28. ¿useTransition / useDeferredValue?

Marcan updates como no urgentes. UI responsive mientras render pesado (filtros, listas). Concurrent features de React 18+.

29. Stale closures en hooks

Callback captura valores viejos si deps incorrectas. Solución: deps correctas, useRef para valor actual, o functional update setCount(c => c+1).

30. ¿React Compiler (Forget)?

Compilador que memoiza automáticamente. Reduce necesidad manual de memo/useMemo. Aún adoptando; entender reconciliación sigue siendo clave.

3. Patrones y Arquitectura (31–40)

31. Container/Presentational

Separar lógica/datos (container) de UI pura (presentational). Hoy: custom hooks + componentes tontos.

32. Compound Components

API flexible: <Select><Select.Option /></Select> comparten estado interno vía context. Radix, Headless UI.

33. Render Props vs HOC

Render prop: función como child. HOC: envuelve componente. Ambos comparten lógica; hooks los reemplazan en muchos casos. Cuidado wrapper hell.

34. Feature-Sliced / por dominio

Carpetas por feature (policies/, auth/) con ui/hooks/api/types. Escala mejor que solo por tipo técnico.

35. Smart vs Dumb components

Smart: conectan datos/estado. Dumb: solo props. Facilita Storybook, tests y reutilización.

36. Atomic Design

Átomos → moléculas → organismos → templates → pages. Útil en design systems; no dogma de carpetas.

37. Colocation

Mantener estilos, tests y lógica cerca del componente que usan. Menos saltos entre archivos.

38. Prop drilling — soluciones

Composición (children), context acotado, state library (Zustand/Redux), React Query para server state.

39. Anti-patterns comunes

useEffect para derivar estado (usar variable/cálculo), context gigante, index keys, mutar state directamente, fetch sin cleanup/abort.

40. Suspense para qué

Declarar UI de loading mientras hijo async (lazy, RSC, data con use). Boundaries anidados para granularidad.

4. Next.js — App Router (41–55)

41. Pages vs App Router

App Router (13+): layouts anidados, RSC por defecto, streaming, loading.tsx. Pages: getServerSideProps/getStaticProps — legacy pero válido.

42. Server vs Client Components

Server: async, acceso DB/secrets, cero JS al cliente. Client: 'use client', hooks, browser APIs. Componer: server padre + client hijo.

43. ¿Cuándo 'use client'?

useState/useEffect, onClick, context providers, librerías solo browser. Mantener boundary lo más bajo posible.

44. Fetch en Server Components

await fetch en componente server; Next dedupe y cache por defecto. cache: 'no-store' dinámico; revalidate: 60 ISR.

45. Route Handlers

app/api/.../route.ts exporta GET/POST. Sustituto de API routes Pages. Edge o Node runtime según necesidad.

46. Middleware Next.js

middleware.ts en edge: auth redirect, locale, headers. Corre antes del render.

47. dynamic() import

Code splitting con loading opcional. ssr: false solo client. Reduce bundle inicial.

48. Metadata API

export const metadata o generateMetadata para SEO, OG tags. Estático o dinámico por ruta.

49. Server Actions

Funciones server invocables desde client forms. Mutaciones sin API REST explícita. Validar siempre en servidor.

50. Hydration mismatch

HTML servidor ≠ primer render cliente (Date.now, window, random). Usar useEffect, suppressHydrationWarning puntual, o render solo client.

51. ISR vs SSG vs SSR

SSG: build time. ISR: SSG + revalidate. SSR: cada request (o cache CDN). Elegir por frescura vs carga.

52. Parallel & Intercepting Routes

@modal slots, (.)photo intercept — modales con URL shareable sin perder contexto de lista.

53. next/image

Lazy load, sizes responsive, WebP/AVIF, evita CLS con width/height. Dominios en next.config.

54. Env variables

NEXT_PUBLIC_* expuesto al browser. Resto solo server. Nunca secrets en client bundle.

55. Caching Next 15

Fetch cache, Full Route Cache, Router Cache cliente. revalidatePath/revalidateTag invalidación on-demand.

5. Estado Global — Redux / Alternativas (56–65)

56. ¿Cuándo Redux?

Estado global complejo, muchas fuentes de updates, time-travel debug, middleware (sagas). Overkill para UI local o server state.

57. Redux Toolkit ventajas

createSlice, Immer inmutable, configureStore, menos boilerplate. Estándar actual vs Redux clásico.

58. Flujo Redux

UI dispatch action → reducer puro → nuevo state → store → selectors → re-render suscriptores.

59. createAsyncThunk

Thunk con pending/fulfilled/rejected. Integra loading/error en slice sin escribir máquina manual.

60. RTK Query

Cache server state en Redux: endpoints, tags, invalidación. Alternativa a React Query si ya usas Redux.

61. Selectores memoizados

createSelector (reselect) evita recalcular derivados y reduce re-renders en useSelector.

62. Redux vs Context

Context: pocos valores, simple. Redux: updates frecuentes, devtools, middleware, normalización. Context no escala con muchos consumidores.

63. Server state vs Client state

Server: React Query/SWR/RTK Query. Client: UI, modals, wizard step. No duplicar API data en Redux sin necesidad.

64. Zustand / Jotai

Stores ligeros sin boilerplate. Zustand: store único. Jotai: átomos. Bueno para estado medio sin Redux.

65. Normalización de estado

Entidades por ID en objetos (byId, allIds). Evita duplicados y facilita updates parciales (patrón Redux en listas).

6. Performance y Optimización (66–80)

66. Cómo medir performance

React Profiler, Lighthouse, Web Vitals (LCP, INP, CLS). Chrome Performance tab. Medir antes de optimizar.

67. React.memo

Evita re-render si props shallow-equal. Útil en listas/items pesados. Comparador custom si props complejas.

68. Virtualización de listas

Render solo filas visibles (react-window, tanstack-virtual). Esencial con 10k+ items. Pluvia/ag-Grid patrón enterprise.

69. Code splitting

React.lazy + Suspense, dynamic() en Next, route-based splitting automático. Bundle por ruta/feature.

70. Web Vitals — LCP

Largest Contentful Paint <2.5s. Optimizar hero image, fonts, SSR, CDN, quitar render-blocking JS.

71. INP (Interaction to Next Paint)

Latencia de interacción. Reducir JS largo, usar transitions, workers, dividir tareas, evitar re-renders masivos en input.

72. CLS

Cumulative Layout Shift: reservar espacio imágenes/fonts, no insertar banners encima de contenido, skeletons con altura fija.

73. Debounce vs Throttle

Debounce: ejecuta tras pausa (búsqueda). Throttle: máximo N veces por intervalo (scroll). Ambos reducen trabajo.

74. Bundle analysis

@next/bundle-analyzer, webpack-bundle-analyzer. Detectar librerías pesadas, tree-shaking, imports específicos.

75. Tree shaking

Eliminar código muerto en build. Import named/ESM; evitar barrel files enormes que impiden shake.

76. Prefetch y preload

Next Link prefetch rutas. rel=preload fonts/critical assets. React Query prefetchQuery en hover.

77. Optimistic updates

UI actualiza antes de respuesta server; rollback si falla. React Query onMutate, Redux optimistic reducer, useOptimistic.

78. Memoización excesiva

Anti-pattern: memo en todo. Coste comparación + complejidad. Optimizar hot paths identificados con profiler.

79. SSR vs CSR trade-offs

SSR: SEO, FCP rápido, más carga servidor. CSR: SPA simple, TTI puede tardar. Híbrido RSC es el sweet spot Next.

80. Workers / Off-main-thread

Comlink, Web Workers para parse CSV, cripto, cálculos pesados sin bloquear INP.

7. TypeScript + React (81–85)

81. Tipar props de componente

type Props = { title: string; onSave?: () => void }. React.FC ya no recomendado; función explícita + children?: ReactNode.

82. Generics en componentes

function List<T>({ items, render }: { items: T[]; render: (i: T) => ReactNode }) — reutilizable type-safe.

83. Event types

ChangeEvent<HTMLInputElement>, MouseEvent<HTMLButtonElement>. Inferir del handler evita errores.

84. Utility types útiles

Pick, Omit, Partial, Record, satisfies para props derivadas de API types.

85. Tipar hooks custom

Return type explícito o inferido. Genéricos en hooks de fetch: useApi<Policy>(url). Never any en boundaries públicos.

8. Testing (86–90)

86. Pirámide de testing front

Muchos unit (dominio, utils), integración (RTL + MSW), pocos E2E (Playwright). No snapshot masivo de árboles.

87. Testing Library filosofía

Testear como usuario: roles, labels, text. getByRole > querySelector. Evitar detalles de implementación.

88. Mocking fetch / API

MSW intercepta red; vi.fn() en Vitest para unit. Probar loading/error/success paths.

89. Vitest vs Jest

API compatible, más rápido con Vite/ESM, vi.mock nativo. Misma mentalidad describe/it/expect.

90. Qué testear en un hook

renderHook + act: estado inicial, transiciones, cleanup, error. Extraer lógica del componente facilita coverage.

9. Accesibilidad y Web (91–95)

91. ARIA cuándo usar

Primero HTML semántico (button, nav, label). ARIA solo si no hay elemento nativo. aria-live para toasts dinámicos.

92. Focus management en modales

Trap focus, aria-modal, devolver focus al trigger al cerrar. Radix/Headless lo implementan.

93. WCAG niveles

A, AA (estándar legal EU), AAA. Contraste 4.5:1 texto normal, teclado completo, textos alternativos.

94. CORS en frontend

Browser bloquea respuestas cross-origin sin headers CORS del server. Proxy Next rewrites o API same-origin. No “arreglable” solo en client.

95. CSP y XSS

Content-Security-Policy limita scripts. Escapar HTML user input; evitar dangerouslySetInnerHTML. DOMPurify si rich text.

10. Diseño de Sistema y Behavioral (96–100)

96. Diseña un dashboard de pólizas

RSC lista inicial + client grid virtualizado. React Query cache + paginación server. Filtros debounced. Error boundaries por widget. Auth en middleware.

97. Manejo de errores en producción

Boundaries UI, toast + log Sentry, retry con backoff, fallbacks degradados, nunca pantalla blanca sin mensaje.

98. Convivencia con legacy jQuery

Islands React en mounts puntuales, contrato de eventos custom, no doble manipulación DOM, migración incremental por ruta.

99. Cómo priorizas deuda técnica

Impacto × esfuerzo × riesgo. Quick wins en hot paths, tests en dominio crítico, ADRs para decisiones, no big-bang rewrite.

100. Pregunta trampa: ¿React es un framework?

Es librería de UI (Vista). Next.js/Remix sí son frameworks full-stack. React no trae router, data layer ni convenciones de proyecto — tú eliges el stack.

Extra A — Manejo de errores (Krunchbox / Pluvia)

Filosofía en B2B enterprise

En Pluvia (analytics retail, 100k+ filas) un fallo en un widget no tumba el dashboard. Errores predecibles, mensajes accionables, sin PII en logs cliente. Validar en boundary, mostrar en UI, reportar en servidor.

Zod en boundary (patrón)

// schemas/policy.ts
export const policyQuerySchema = z.object({
  retailerId: z.string().uuid(),
  from: z.coerce.date(),
  to: z.coerce.date(),
})

export function parsePolicyQuery(raw: unknown) {
  const parsed = policyQuerySchema.safeParse(raw)
  if (!parsed.success) {
    return { success: false as const,
      error: parsed.error.flatten().fieldErrors }
  }
  return { success: true as const, data: parsed.data }
}

// route.ts → 400 si !success
// hook → nunca asumir shape del API sin validar

Hook + grid (Pluvia-style)

function useGridData(filters: Filters) {
  const [state, setState] = useState<
    'idle' | 'loading' | 'error' | 'success'
  >('idle')
  const [error, setError] = useState<AppError | null>(null)

  useEffect(() => {
    const ctrl = new AbortController()
    setState('loading')
    fetchGrid(filters, { signal: ctrl.signal })
      .then(res => {
        if (!res.ok) throw toAppError(res) // mapea status → code
        return res.json()
      })
      .then(json => {
        const parsed = gridResponseSchema.safeParse(json)
        if (!parsed.success) throw new AppError('INVALID_RESPONSE')
        setState('success')
        return parsed.data
      })
      .catch(err => {
        if (err.name === 'AbortError') return // filtro nuevo, ignorar
        setError(err)
        setState('error')
      })
    return () => ctrl.abort()
  }, [filters])

  return { state, error, retry: () => ... }
}

// Retry: solo GET / lecturas idempotentes
// POST guardar: no auto-retry; confirmar usuario

Qué NO hacer (entrevista)

  • catch {} vacío o solo console.log
  • Mostrar stack trace al usuario final
  • Loguear PII (email, policyId) en Sentry cliente
  • Retry automático en POST de pago/guardado
  • Un Error Boundary global sin fallbacks por sección
  • Confiar en shape del API sin Zod/runtime check

Respuesta entrevista (30 s)

“Capas: Zod en el boundary del API, Result tipado en servicios, estados loading/error/empty en cada widget. Error Boundaries por chart y grid para que un fallo no tire el dashboard. Retry solo en lecturas idempotentes con AbortController en filtros. Logs a Sentry en servidor; en cliente mensajes humanos sin datos sensibles. En Pluvia con ag-Grid SSRM usamos overlay de error y refetch del datasource.”

Extra B — useMemo / useCallback: cuándo SÍ y cuándo NO

Regla de oro

Medir primero (React Profiler). Memoizar tiene coste: comparar deps + memoria. En Krunchbox/Pluvia solo optimizamos hot paths: celdas de grid, columnDefs, handlers pasados a memo children, filtros sobre datasets grandes.

useMemo — SÍ usar

CasoPor qué
Cálculo caroFiltrar/ordenar 10k–100k filas, agregaciones
Referencia estableObjeto/array pasado a hijo memo() o useEffect deps
columnDefs ag-GridEvitar recrear defs cada render → grid no parpadea
Context valueuseMemo(() => ({ user, theme }), [user, theme])
Derivar de propsvisibleRows = rows.filter(...) si filter es O(n) grande

useMemo — NO usar

CasoAlternativa
Suma, map pequeño (<100 items)Cálculo directo en render
“Por si acaso” sin profilerNada — YAGNI
Primitivos (n * 2)Variable normal
Estado que debería ser stateuseState + effect o derived en evento

useCallback — SÍ usar

CasoPor qué
Hijo React.memoMisma ref de función → skip re-render
Deps de useEffectEvitar re-run infinito del effect
Virtual list / grid cellRenderer estable por fila (miles de nodos)
Callback a lib externaag-Grid onFilterChanged, DnD sensors
Custom hook APIExponer onSave estable al consumidor

useCallback — NO usar

CasoPor qué
Hijo sin memoRe-renderiza igual; callback no ayuda
Handler en botón sueltoCoste re-render negligible
Dentro de listas sin memo itemN funciones nuevas igualmente
Deps cambian cada renderuseCallback(fn, [obj]) inútil si obj es nuevo

Árbol de decisión rápido

¿El cálculo tarda >1ms en Profiler?
  SÍ → useMemo
  NO → cálculo inline

¿El hijo está envuelto en memo()?
  SÍ → useCallback para props función
  NO → handler inline OK

¿La referencia está en deps de useEffect?
  SÍ → useCallback o mover lógica dentro del effect
  NO → no necesario

¿React Compiler / Forget activo en proyecto?
  SÍ → menos memo manual; seguir midiendo
  NO → optimizar solo hot paths identificados

Respuesta entrevista (20 s)

“No memoizo por defecto. Uso useMemo para cálculos caros o referencias estables en grids y context; useCallback cuando paso funciones a hijos memoizados o como deps de effects. En Pluvia perfilamos con Profiler: columnDefs, cell renderers y filtros sobre 100k filas. El resto del árbol se optimiza con virtualización y state colocado, no con memo en todo.”
